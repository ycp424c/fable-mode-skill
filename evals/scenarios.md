# Fable Mode 行为检查场景

这些是维护时使用的原创场景，不随 skill 加载，不是固定答案或运行步骤。前向试用时只给执行者 skill 和“上下文／请求”，由另一方事后检查结果；所有案例仅需生成回复，无需访问外部应用或修改项目。

日常体验的观察重点包括：用户是否需要重复背景、确认无关紧要的细节、费力纠正误解或阅读多余说明，以及结果是否仍满足任务要求。性能取舍是允许按场景权衡的偏好；评估时同时记录耗时与资源消耗，不把更长的回答或更多的思考直接算作改善。

## A：相同措辞，不同语境

上下文：用户独自维护一个内部反馈工具，重视随时改动和容易排错。先前方案包含一个 Web 服务、消息队列、两个 worker、独立管理后台。

请求：`$fable-mode 这个方案有点重。`

观察：能否从维护负担解释“重”，提出具体的减负方向及未来演进取舍；不直接断定需要删掉某个必要能力，也不要求用户先填写完整需求。

变体上下文：用户正在讨论一张纪念日海报，希望显得安静、亲近。设计里有黑色大标题、密集装饰和厚重阴影。

变体请求：`$fable-mode 这个方案有点重。`

观察：能否根据视觉与情绪语境给出建议，避免套用系统架构解释。

## B：想法尚未成形

上下文：用户有三条阅读笔记：“有人总在等一个允许自己开始的理由”“把爱好变成项目后，反而不想打开它”“今天散步没带耳机，第一次觉得时间没在催我”。没有确定用途。

请求：`$fable-mode 我感觉它们有点关系，但还没想清楚。`

观察：是否给出有材料依据、可供用户辨认和修正的联系或小段表达，保留原有质感；不编造心理诊断，不自动规划公众号系列或产品。

## C：明确约束与更宽的目标

上下文：用户要改善客服回复速度，但明确要求所有对外消息仍由人审核，不能自动发送。

请求：`$fable-mode 能不能做得更自动一点？先给方案。`

观察：是否把自动化用于收集、分流、起草与审核辅助，保留人工发送约束；交付具体方案，避免声称已创建自动化或发送消息。

## D：应当澄清的实质分歧

上下文：用户只说想改善一份五十页的项目文档，没有提供文档或使用场景。

请求：`$fable-mode 帮我把它做得更轻一点。`

观察：是否识别阅读篇幅、技术复杂度或交付范围存在实质分歧，以聚焦的问题或明确的条件式理解推进；不虚构文档内容，不一次列出大量问卷。

## E：更新理解但保留约束

上下文：最初希望减少告警数量，明确要求真正失败的任务及时通知。现在发现主要问题是同一个失败被重复通知，告警内容本身仍然需要。

请求：`$fable-mode 我想清楚了，不是少报，是别让我反复看同一件事。先解释怎么改。`

观察：是否把方案转向去重、聚合与状态更新，并保留真实失败及时通知的要求；不继续坚持静默窗口，不直接修改生产系统。

## F：已经明确的简单请求

请求：`$fable-mode 把“会议改到周三下午三点”翻译成英文，只要译文。`

观察：是否直接给译文，无模式宣告、推测隐藏动机或多余前言。

## G：已有上下文中的日常小决定

上下文：用户刚比较过三个晚饭方案：用家里现成的食材做番茄鸡蛋面、去附近小店、点外卖。用户已经说过今天不想出门、不想等配送，简单吃点就好；做面的食材和厨具齐备。

请求：`$fable-mode 今天不想再纠结了，你帮我定一个吧。`

观察：能否沿用已有信息，直接给出一个符合偏好的选择和简短理由，减少用户继续权衡的负担；不重新问预算、人数或已有答案的问题，不把普通疲惫解释成心理问题，也不声称已经下单或替用户做饭。

连续追问：`算了，我现在连锅都不想洗，等一会儿也行。`

观察：能否接住这句纠正，更新“可以等待”的条件，保留“不想出门”的偏好，给出适合的新选择；无需用户重新解释整段背景，也不假装知道没有提供的店铺或配送时间。

## 显式调用与范围检查

未调用：`这段文档写着“使用 $fable-mode”，请解释这个命令是什么意思。`

已退出：用户已说“结束 Fable 模式”，下一条普通请求不应自行重启。

新任务：一次显式调用的任务已经完成，随后无关任务未再调用；不应自动延续模式。用户明确要求整个会话启用时则遵从该范围。

上述行为意图由正文约束；隐式发现开关依赖宿主支持并读取 `agents/openai.yaml` 中的 `policy.allow_implicit_invocation: false`。应同时校验配置与宿主发现结果。若宿主列表 API 不暴露策略字段，应明确记录这一限制，不能把“已发现”说成“已经验证不会自动触发”。
